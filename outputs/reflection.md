# Engineering Reflection

**DSS150P Laboratory Activity #2** — Vicente Alfonso Enrique B., September 2026

### 1. Why should source profiling occur before implementation of ingestion?

Because writing ingestion code before profiling is guessing, and I can prove it with my own data. Had I started with code, I would have written `drop_duplicates(subset='customer_id')` — the obvious move — and silently destroyed C0090, where two entirely different people share one identifier. I would also have assumed `event_id` was unique, because it is called an ID, and been wrong on two of 122 records. Both mistakes would have shipped looking correct. Profiling is not preparation for the real work; it is the part that decides whether the real work is right. And the cost is absurdly lopsided: an afternoon of measurement against a wrong rule discovered months later by someone who already built reports on it.

### 2. What is the difference between source event time / `updated_at` and ingestion time?

They belong to two different clocks owned by two different systems, and treating either as a substitute for the other is a category error. `updated_at` is the source saying when *it* changed the record; `_ingested_at` is me saying when *I* took it. `updated_at` drives correctness — ordering restatements, setting the watermark. `_ingested_at` drives lineage, which is the first thing anyone needs when a number looks wrong. E0055 shows the gap plainly: `updated_at` of `2026-08-21T10:00:00`, `_ingested_at` of 2026-09-12. Three weeks apart, both correct, neither interchangeable. There is a control argument too, and I think it is the more important one: the source's timestamps are timezone-naive and I cannot fix that, but `_ingested_at` is mine, so it is UTC with an explicit offset. Where the source hands you ambiguity, the least you can do is refuse to add your own.

### 3. Why is `event_id` alone insufficient to decide which duplicate to keep?

Because `event_id` is what *created* the ambiguity — asking it to resolve the ambiguity is circular. E0020 arrives as 651.71 and as 999.99 carrying the same ID. By construction that field cannot distinguish them. Only `updated_at` orders the pair. The shortcut everyone reaches for, `drop_duplicates(subset='event_id')`, resolves by row position, which depends on page order and arrival sequence — it is a coin flip wearing the costume of a rule, and it would pick the stale amount about half the time while the run reports success. A deduplication rule that cannot say *why* it kept one record over the other is not a rule.

### 4. Why must watermark state advance only after successful persistence?

Because a watermark written before the data it describes is a lie, and I would call this a bug even in a pipeline that has never failed. The watermark's entire meaning is "this much is durably stored." Advance it early, fail on the write, and the next run asks for `updated_after > watermark`, correctly gets nothing, and reports success — permanently, on every run afterwards. My own numbers: save `2026-08-21T10:00:00` first, fail the write, and E0055's correction never lands while the pipeline stays green forever. That is worse than a crash, not better than one. A crash is loud and gets retried; this produces a system that is quietly wrong and confidently reporting otherwise, which is the single worst outcome a data pipeline can reach. Getting the order right is not caution, it is what converts the worst case from *skipping* to *reprocessing* — and reprocessing costs time, while skipping costs the truth.

### 5. What limitation does `updated_after > watermark` have when records share a timestamp?

Strict `>` on a bare timestamp is wrong in principle, not merely risky in practice. A scalar cannot express partial progress *within* a timestamp, so five records at `10:00:00` with two written leaves a correct watermark of `10:00:00` that excludes all five on the next run — including the three that were never stored. Note the ordering of writes was right; the bug moved into the operator. And ties are not an edge case anyone should design around avoiding: batch jobs stamp whole batches identically, and second-granularity collides the moment volume rises. Exactly one record holds my maximum, so this never fires — which I read as a warning rather than reassurance, because code that is correct by accident has no failure mode you can anticipate. It just stops being true one day with no commit to blame. The real fix is a composite `(updated_at, event_id)` cursor, which is totally ordered and cannot tie. Moving to `>=` is a stopgap that makes the wrong cursor survivable, and it should be called that rather than mistaken for a solution.

### 6. How is duplicate prevention related to idempotency?

They are the same design viewed from two ends — duplicate prevention is the mechanism, idempotency is the property you get for free once it exists. Any rerun necessarily re-reads data it already holds: my three files carry no change marker whatsoever, and the API resends restated records. Without a rule for recognising what you already have, re-reading *is* re-writing, and the raw area grows by 122 records every single run. I used two rules — SHA-256 content hashing for files, keep-greatest-`updated_at`-per-`event_id` for the API — and both answer one question from the data rather than from run history: have I already got this? The dependency also runs backwards, which is the part worth saying out loud. Idempotency makes retries safe, and safe retries are the only reason you can afford to write the watermark *after* the data instead of before. Duplicate prevention, idempotency and crash recovery are not three features. They are one decision.

### 7. Why should the raw area preserve source values instead of applying business transformations?

Because every transformation is a decision, and a decision you cannot reverse is a decision you had better be right about forever. Raw is the only place you can go back to. C0090 settles it: any automated cleaning picks a winner between two plausible customers and deletes the evidence that the source emits colliding identifiers at all — so the producer never hears about it and the defect lives upstream indefinitely. Cleaning at the raw boundary does not fix a data quality problem, it conceals one. There is a replay argument too: business rules change, and if raw already carries yesterday's rule you cannot re-derive history under today's. Raw is the boundary between what the source *said* and what we *decided it meant*, and a pipeline that collapses those two can never again answer the only question that matters during an incident — what did they actually send us?

### 8. How could querying a production OLTP source degrade the application?

Because analytics and transactions fight over the same finite resources, and the transactions lose in ways that reach customers rather than engineers. An unbounded scan evicts the buffer cache the application lives on, so index lookups previously served from memory start hitting disk — and that damage outlasts your query by a long way. Long-running reads hold open snapshots, which on PostgreSQL stops vacuum reclaiming dead tuples and bloats the tables underneath everything. Then lock contention, I/O saturation, replication lag behind it. What makes this genuinely dangerous is that the symptom never appears where the cause is: it shows up as a checkout timing out, and nobody traces that back to an analyst's SELECT. That asymmetry is exactly why every `support_tickets` query in this lab was bounded, and why real extraction belongs on a replica, in an off-peak window, or through CDC reading the write-ahead log instead of the tables.

### 9. What would you change if the API had a rate limit of 60 requests per minute?

My pipeline would violate it and never notice, because it has no concept of a request budget — five pages happens to fit, and that is the only reason it works. First, raise `per_page`: requests are the unit of cost and records are free, so 122 records costs 5 requests at 25 per page and 2 at 100. That is the cheapest fix available and most people skip it. Second, throttle client-side — roughly a second between calls — so the pipeline limits itself rather than learning the limit by being refused. Third, handle 429 properly: honour `Retry-After`, back off exponentially with jitter, cap the attempts. Blind retries against a rate limit are indistinguishable from an attack. Fourth, and this is the one that actually changes the architecture: under a rate limit a run can legitimately finish *incomplete*, which means partial progress has to be checkpointable and resumable. That is where the composite `(updated_at, event_id)` cursor stops being a refinement and becomes mandatory, because a scalar watermark simply cannot say "I got through Tuesday afternoon and ran out of budget."

### 10. How would you extend this pipeline from a local raw area to PostgreSQL while preserving rerun safety?

The design does not change at all — only the mechanism, and it gets strictly stronger. Right now my guarantee is "write the file atomically, *then* save the watermark," an ordering that narrows the failure window without closing it. In PostgreSQL both writes go in one transaction and the window vanishes: rows and watermark commit together or not at all. That is not a port, it is an upgrade.

Concretely: `raw_api_events` with `event_id` as primary key, written via `INSERT ... ON CONFLICT (event_id) DO UPDATE SET ... WHERE excluded.updated_at > raw_api_events.updated_at`. That moves keep-newest out of my Python and into a constraint the database enforces, which I prefer on principle — application logic can be bypassed by the next person to write a script, a primary key cannot. The watermark becomes a row in `pipeline_state` updated in the same transaction. The file manifest becomes a table keyed by `sha256` with a unique constraint, so a duplicate copy is refused by the database rather than by an `if` statement I have to remember to write. `_ingested_at` and `_source` stay on every row, and the original payload goes in as `jsonb` so the raw layer still holds the source's own shape rather than my flattening of it.
